# Алерты Victory Group Task Scheduler

Приложение из ДЗ №1 работает в minikube (namespace `task-scheduler`). Метрики из ДЗ №4 собирает VictoriaMetrics, правила SLO из ДЗ №5 считает vmalert (namespace `monitoring`). В этом ДЗ добавлены:
- правила алертов на метрики сервиса, фреймворка и рантайма;
- Alertmanager с уведомлениями в Telegram;
- учения, которые вызывают срабатывание алертов.

## Состав и запуск

| Файл | Что внутри |
|---|---|
| `k8s/alerting/alerts.yaml` | правила алертов vmalert: группы `service`, `framework`, `runtime` |
| `k8s/alerting/alertmanager.yaml` | конфигурация Alertmanager: маршрутизация, подавление, получатель Telegram |
| `k8s/alerting/telegram.tmpl` | шаблон сообщения в Telegram |
| `k8s/alerting/vmalert-alerting-values.yaml` | values поверх `k8s/slo/vmalert-values.yaml`: включает Alertmanager в чарте `victoria-metrics-alert`, подключает `alerts.yaml` вторым `-rule` |
| `k8s/alerting/telegram-secret.sh` | спрашивает токен бота и chat id и сохраняет их в Secret `alertmanager-telegram` |
| `k8s/alerting/install.sh` | ConfigMap с правилами и конфигом Alertmanager, `helm upgrade` релиза `vmalert` |
| `k8s/slo/fault.sh` | учения: `errors`, `memory`, `bad-logins`, `off` |
| `services/core-api/app/fault_injection.py` | инъекция сбоев в core-api, добавлен балласт памяти `CORE_FAULT_MEMORY_MB` |

```bash
./k8s/alerting/telegram-secret.sh   # токен бота и chat id → Secret (в репозиторий не попадают)
./k8s/alerting/install.sh           # правила + Alertmanager
kubectl -n monitoring port-forward svc/vmalert-victoria-metrics-alert-server 8880:8880
# алерты: http://localhost:8880/vmalert/alerts
kubectl -n monitoring port-forward svc/vmalert-victoria-metrics-alert-alertmanager 9093:9093
# Alertmanager: http://localhost:9093
```

```
vmagent ──► VictoriaMetrics ◄── vmalert: правила ДЗ5 (SLO) + alerts.yaml (ДЗ6)
                                   │ -notifier.url
                                   ▼
                              Alertmanager ── группировка, подавление ──► Telegram-бот
```

Токен бота хранится только в Secret. Alertmanager читает его из файла (`bot_token_file`), в values и ConfigMap токена нет. Chat id подставляется в конфиг при установке.

## Какие алерты и почему

Алерт заводится только на то, по чему понятно, что делать. У каждого есть:
- `severity`: `critical` — действовать сейчас, `warning` — разобраться в рабочее время;
- `layer`: на каких метриках построен;
- `summary` и `description`: они попадают в сообщение.

Порог выбран так, чтобы одиночный всплеск не будил, а `for` подтверждает, что проблема держится.

### Метрики сервиса (`service`)

Бизнес-метрики `taskscheduler_*` из ДЗ4 и очередь RabbitMQ.

| Алерт | Условие | Почему так |
|---|---|---|
| `LoginFailuresSpike` (warning) | неудачных входов больше 0,2/с (12 в минуту) за 5 мин, держится 2 мин | человек, забывший пароль, делает несколько попыток, а не десятки: это подбор пароля |
| `AutomationEventsFailing` (warning) | `increase(taskscheduler_automation_events_total{result="failed"}[10m]) > 0` | automation-worker не обработал событие, и пользовательское правило молча не сработало. Правила редкие, поэтому важна любая ошибка |
| `AutomationQueueBacklog` (warning) | в RabbitMQ больше 50 готовых сообщений 5 мин | automation-worker упал или не успевает: автоматизации выполняются с опозданием |
| `IncidentWebhookErrors` (warning) | `increase(taskscheduler_incidents_total{result="error"}[10m]) > 0` | негативный отзыв не превратился в задачу-инцидент, то есть потерян для клиента |

Вместе с ними в Telegram теперь уходят алерты ДЗ5 на SLO:
- `AvailabilityBudgetFastBurn`, `LatencyBudgetFastBurn` — бюджет ошибок сгорает в 14,4 раза быстрее нормы;
- `ProberFailing` — синтетический пользователь не может открыть доску;
- `ReviewPipelineStalled` — пайплайн отзывов стоит;
- `SLAAtRisk` — под угрозой SLA.

Это главные алерты на пользовательский опыт. Новые правила дополняют их тем, чего SLO не видит.

### Метрики фреймворка (`framework`)

Метрики FastAPI от `prometheus-fastapi-instrumentator` в core-api и ml-worker.

| Алерт | Условие | Почему так |
|---|---|---|
| `ApiHighErrorRate` (critical) | доля 5xx больше 5 % за 2 мин, держится 2 мин, по каждому приложению | сломалась зависимость или код: пользователи получают ошибки. Порог по каждому FastAPI-приложению, в отличие от burn rate, который есть только у core-api |
| `ApiSlowRequests` (warning) | больше 10 % успешных запросов дольше 0,5 с, держится 5 мин | 0,5 с — граница корзины гистограммы. Деградация заметна, но не авария |

### Метрики рантайма (`runtime`)

Метрики процесса Python от `prometheus-client` (`process_*`) и `up` от vmagent.

| Алерт | Условие | Почему так |
|---|---|---|
| `PythonProcessMemoryHigh` (warning) | `process_resident_memory_bytes` больше 75 % лимита памяти контейнера (512/384/256 МиБ у core-api/ml-worker/automation-worker), держится 2 мин | следующий шаг — OOMKilled и рестарт. 25 % запаса дают время найти утечку до падения |
| `PythonProcessRestarting` (critical) | `changes(process_start_time_seconds[15m]) >= 2` | процесс падает по кругу (crash loop). Имя пода при рестарте контейнера не меняется, поэтому смена времени старта видна в той же серии |
| `MetricsTargetDown` (critical) | `up == 0` 2 мин (8 неудачных опросов) | процесс завис: Kubernetes считает под Running, но он не отвечает |
| `PythonProcessFdsExhausted` (warning) | открытых дескрипторов больше 80 % лимита, держится 5 мин | утечка соединений или файлов, скоро будет «Too many open files» |

## Alertmanager

Alertmanager включён в тот же Helm-релиз `vmalert` (чарт `victoria-metrics-alert` 0.50.0, Alertmanager v0.34.1). Конфигурация — `alertmanager.yaml`:

- **Группировка** `group_by: [alertname]`. Одно сообщение на алерт, даже если он горит на обеих репликах core-api.
- **Тайминги:**
  - `group_wait: 30s` — собрать группу перед первым сообщением;
  - `group_interval: 2m` — изменения в группе отправлять не чаще раза в 2 минуты;
  - `repeat_interval` — напоминание: 1 ч для `critical`/`page`, 4 ч для `warning`.
- **Подавление:**
  - когда горит `MetricsTargetDown`, предупреждения того же пода не шлются: под не отвечает, его память и задержки ничего не добавляют;
  - когда горит `ApiHighErrorRate`, не шлётся `ApiSlowRequests` того же приложения.
- **Получатель** — бот Telegram, `send_resolved: true`: приходит и срабатывание, и восстановление. Сообщение по шаблону `telegram.tmpl`: статус, имя алерта, severity, слой, описание, под и время.

## Учения: как показать срабатывание

| Команда | Что меняется | Какой алерт сработает |
|---|---|---|
| `./k8s/slo/fault.sh errors 0.3` | 30 % запросов к API core-api получают 503 | `ApiHighErrorRate` (фреймворк), из ДЗ5 — `AvailabilityBudgetFastBurn`, `SLAAtRisk` |
| `./k8s/slo/fault.sh memory 350` | core-api при старте удерживает 350 МБ, как при утечке: RSS около 460 МБ при лимите 512 | `PythonProcessMemoryHigh` (рантайм) |
| `./k8s/slo/fault.sh bad-logins` | ~3 мин входов под несуществующими email (перебор логинов), 2 в секунду. В демо-режиме `CORE_DEV_LOGIN=true` пароль не проверяется, поэтому неудачный вход — это неизвестный пользователь | `LoginFailuresSpike` (сервис) |
| `./k8s/slo/fault.sh off` | всё возвращается | приходят сообщения RESOLVED |

Балласт памяти (`CORE_FAULT_MEMORY_MB`) — третий вид инъекции в core-api, рядом с ошибками и задержкой из ДЗ5. По умолчанию выключен. При старте процесс выделяет и заполняет буфер заданного размера, поэтому `process_resident_memory_bytes` растёт ровно как при утечке.

Учение с ошибками показало, зачем нужны алерты на разных уровнях. Одна причина (core-api отвечает 503) дала:
- алерт фреймворка: доля 5xx;
- алерт SLO: пробер не проходит сценарий;
- алерт сервиса: потерянные инциденты.

По сообщению сервисного уровня видно, что задело бизнес-процесс, а по сообщению фреймворка — где искать причину.
