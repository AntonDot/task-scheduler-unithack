# Стратегии деплоя Victory Group Task Scheduler

Приложение из ДЗ №1 работает в minikube (namespace `task-scheduler`), метрики собирает VictoriaMetrics, дашборды — Grafana из ДЗ №7. В этом ДЗ перед приложением поставлен **Envoy Gateway** (реализация Gateway API), и на **core-api** показаны пять стратегий обновления:
- Rolling;
- Blue/Green;
- Canary;
- A/B;
- Shadow.

Трафик между версиями делит `HTTPRoute`. Приложение для этого не меняется: новая версия — это новый образ.

## Что требовалось и как сделано

| Требование | Как выполнено |
|---|---|
| несколько подов, реплики ≥ 2 | основной Deployment `core-api` — 2 реплики (на время rolling — 4), `core-api-v1` и `core-api-v2` — по 2 |
| состояние вне пода | данные — PostgreSQL, вложения — S3, события WebSocket между репликами — PostgreSQL `LISTEN/NOTIFY`, дедупликация внешних событий — таблица `external_events`. Обе версии работают с одной базой, поэтому запрос может попасть на любую реплику любой версии |
| readiness/liveness-пробы | readiness `/ready` проверяет базу (`SELECT 1`), liveness `/health` — что процесс отвечает. Init-контейнер `wait-for-migrations` не пускает под в работу до нужной схемы БД |
| версия в ответе или метрике | версия вшивается в образ (`APP_VERSION`) и видна в четырёх местах: `GET /api/v1/version`, заголовок `X-App-Version` во всех ответах, метрика `taskscheduler_build_info{version}`, поле `service.version` в логах |
| Envoy Gateway по образцу demo | Envoy Gateway v1.10.0 со стандартными CRD Gateway API, GatewayClass и Gateway `eg`, доступ через port-forward к Envoy-прокси (на minikube LoadBalancer остаётся Pending) |
| Rolling, Blue/Green, Canary 90/10 → 50/50 → 0/100, A/B по заголовку, Shadow | `demo.sh <стратегия>` — прогон каждой, логи в `logs/`, видео — `videos/` |

## Состав и запуск

| Файл | Что внутри |
|---|---|
| `services/core-api/app/version.py` | версия процесса (`APP_VERSION` из образа) и имя пода |
| `services/core-api/app/main.py` | `GET /api/v1/version`, middleware с заголовком `X-App-Version`, версия в `/health` |
| `services/core-api/app/metrics.py` | метрика `taskscheduler_build_info{version}` = 1 |
| `services/core-api/tests/test_version.py` | тесты эндпоинта, заголовка и метрики |
| `k8s/deploy-strategies/install.sh` | Envoy Gateway, образы `core-api:v1.0.0` и `:v2.0.0`, Gateway |
| `k8s/deploy-strategies/00-gateway.yaml` | GatewayClass `eg`, Gateway `eg`, HTTPRoute `web` (`/` → фронт) |
| `k8s/deploy-strategies/01-backend-traffic-policy.yaml` | Envoy закрывает простаивающие соединения к подам через 4 с, раньше uvicorn (см. A/B) |
| `k8s/deploy-strategies/app/core-api-v1.yaml`, `core-api-v2.yaml` | две версии core-api рядом: Deployment + Service |
| `k8s/deploy-strategies/strategies/*/` | HTTPRoute `core-api` (`/api`, `/ws`) для каждой стратегии |
| `k8s/deploy-strategies/traffic.sh` | непрерывный трафик через Envoy на `/api/v1/version`, печатает версию и под |
| `k8s/deploy-strategies/demo.sh` | проводит стратегию по шагам, после каждого шага считает доли версий, пишет лог |
| `k8s/deploy-strategies/logs/*.log` | логи прогонов |
| `k8s/grafana/dashboards/deploy-strategies.json` | дашборд Grafana «Стратегии деплоя core-api» |

```bash
./k8s/deploy-strategies/install.sh            # Envoy Gateway + образы v1/v2 + Gateway
./k8s/deploy-strategies/demo.sh rolling       # и blue-green, canary, ab, shadow
./k8s/deploy-strategies/demo.sh reset         # вернуть исходное состояние
./k8s/deploy-strategies/traffic.sh            # просто трафик, в отдельном терминале
```

```
                    ┌──────────── Envoy Gateway (envoy-gateway-system) ────────────┐
браузер / curl ──► Envoy-прокси  Gateway eg :80
                    │   HTTPRoute web:       /          → Service web (SPA)
                    │   HTTPRoute core-api:  /api, /ws  → по стратегии:
                    │        rolling     → Service core-api   (Deployment core-api, v1 → v2 по одному поду)
                    │        остальные   → Service core-api-v1 / core-api-v2 (веса, заголовок, зеркало)
                    └───────────────────────────────────────────────────────────────┘
core-api-v1 ×2, core-api-v2 ×2, core-api ×2 ──► общие PostgreSQL, S3, RabbitMQ
```

У подов `core-api-v1/-v2` метка `app=core-api-v1/-v2`, а не `app=core-api`. Поэтому основной Service `core-api`, через который ходят nginx фронта, ml-worker и automation-worker внутри кластера, по-прежнему смотрит только на основной Deployment. Стратегия управляет трафиком, который приходит через Gateway, а внутренние вызовы не перемешиваются между версиями.

## Как устроена каждая стратегия и что показал прогон

Прогоны записаны на видео 25.11.2026 с 22:19 до 22:32. Трафик `traffic.sh` — около 4 запросов в секунду, каждый шаг длится 20 с. Цифры из `logs/<стратегия>.log`: строка «ответы за шаг» — все запросы с начала шага, «последние 20» — что отвечает к концу шага.

### Rolling — постепенная замена подов

Один Deployment `core-api`, `strategy.rollingUpdate: maxSurge 1, maxUnavailable 0`. HTTPRoute ничего не делит, весь `/api` идёт на Service `core-api` (`strategies/rolling/httproute.yaml`). `demo.sh` меняет образ `v1.0.0` → `v2.0.0` командой `kubectl set image`, Kubernetes поднимает новый под, ждёт readiness, гасит старый — и так 4 раза. Затем `kubectl rollout undo` тем же способом возвращает v1.

| Шаг | Ответы за шаг | К концу шага |
|---|---|---|
| исходно, 4 пода v1.0.0 | v1 — 75 (100 %) | v1 ×20 |
| `set image … v2.0.0`: первый ответ v2 через 3 с, последний ответ v1 через 11 с | v1 — 31 (25,8 %), v2 — 89 (74,2 %), вперемешку | v2 ×20 |
| `rollout undo` | v1 — 90 (73,8 %), v2 — 32 (26,2 %) | v1 ×20 |

317 запросов за прогон, **ни одной ошибки**. Новый под получает трафик только после readiness, старый уходит после появления замены (`maxUnavailable: 0`), а uvicorn дорабатывает начатые запросы при SIGTERM. Поэтому в списке подов сразу после `rollout status` ещё виден один под v1: он завершается и успевает ответить на последние запросы. В логе видны ревизии ReplicaSet: 42 (`v1.0.0`) → 43 (`v2.0.0`, 4 реплики). `rollout undo` создаёт новую ревизию 44 с образом `v1.0.0`, а не «возвращается» на 42.

### Blue/Green — мгновенное переключение и откат

Обе версии подняты и прогреты (`app/core-api-v1.yaml`, `app/core-api-v2.yaml`). HTTPRoute целиком указывает на одну из них: `httproute-green.yaml` → `core-api-v1`, `httproute-blue.yaml` → `core-api-v2`. Переключение и откат — `kubectl apply` одного файла: Envoy получает новую конфигурацию за доли секунды, поды не перезапускаются.

| Шаг | Ответы за шаг |
|---|---|
| green: весь трафик на v1 | v1 — 77 (100 %) |
| переключение на blue | v2 — 75, v1 — 1 (запрос, пришедший в момент `apply`) |
| откат на green | v1 — 75, v2 — 1 |

229 запросов, ошибок нет. В отличие от rolling, смеси версий нет: трафик целиком на одной из них. Откат такой же мгновенный, потому что green всё время работал. Цена — двойные ресурсы на время переключения.

### Canary — 90/10 → 50/50 → 0/100

Одно правило HTTPRoute с двумя `backendRefs` и весами (`strategies/canary/httproute-90-10.yaml`, `-50-50`, `-0-100`). Envoy выбирает бэкенд для каждого запроса с вероятностью веса. Откат на любом шаге — применить файл с меньшим весом v2.

| Веса v1/v2 | Ответы за шаг (20 с) |
|---|---|
| 90/10 | v1 — 66 (88,0 %), v2 — 9 (12,0 %) |
| 50/50 | v1 — 40 (52,6 %), v2 — 36 (47,4 %) |
| 0/100 | v2 — 75 (100 %) |

226 запросов, ошибок нет. Доли совпадают с весами с точностью до случайности выборки из ~75 запросов. Между шагами можно смотреть на ошибки и латентность v2 на дашборде и решать, идти дальше или откатываться.

### A/B — по заголовку на выбранную аудиторию

Не случайная доля, а конкретная группа (`strategies/ab/httproute-ab.yaml`). Первое правило — путь `/api` и заголовок `x-user-group: beta` → v2. Второе — всё остальное → v1. Gateway API сначала проверяет более специфичное правило. Так же можно выбирать по query-параметру, методу или cookie.

Два потока трафика одновременно:

| Поток | Ответы за шаг |
|---|---|
| обычные пользователи | v1 — 75 (100 %) |
| `x-user-group: beta` | v2 — 74, один ответ 503 (см. ниже) |

Проверка вручную в логе: без заголовка — `v1.0.0`, с `x-user-group: beta` — `v2.0.0`, с `x-user-group: alpha` — `v1.0.0`. Разделение детерминированное: один и тот же пользователь всегда попадает в свою версию, в отличие от canary.

**Единственная ошибка за все прогоны.** В 22:30:13 один запрос группы beta получил 503. Его отдал Envoy, а не приложение: в access-логе Envoy `response_flags: UC`, `upstream_reset_before_response_started{connection_termination}`. Это гонка keep-alive. Envoy держит простаивающее соединение к поду до часа, uvicorn закрывает его через 5 с. Запрос, отправленный в соединение, которое как раз закрывается, обрывается. Всего через Envoy за вечер прошло 3828 запросов, это единственный такой случай.

Исправление — `01-backend-traffic-policy.yaml`: `BackendTrafficPolicy` с `connectionIdleTimeout: 4s` на весь Gateway. Прокси должен закрывать простаивающее соединение раньше бэкенда. В конфигурации Envoy у кластеров теперь `idle_timeout: 4s`. Нарочно воспроизвести гонку не удалось (по 40 запросов с интервалом около 5 с, 0 ошибок и до, и после политики), поэтому эффект подтверждается только устройством ошибки, а не замером.

### Shadow — зеркалирование копии трафика

Пользователю отвечает v1, Envoy отправляет копию запроса на v2 и отбрасывает её ответ (фильтр `RequestMirror`, `strategies/shadow/httproute-shadow.yaml`). Зеркалируются **только GET**: обе версии пишут в одну базу, и зеркальный POST/PATCH/DELETE выполнился бы дважды — двойная задача, повторный перенос по колонкам. Поэтому первое правило — `GET /api` с зеркалом, второе — остальные методы только на v1.

| Проверка | Результат |
|---|---|
| ответы пользователю за 20 с | v1 — 75 (100 %), v2 не отвечает никому |
| access-логи `GET /api/v1/version` за тот же период | core-api-v1 — 75, core-api-v2 — 76: копия дошла на каждый запрос (лишний — запрос, пришедший на границе окна подсчёта) |
| `POST /api/v1/auth/token` | core-api-v1 — 1, core-api-v2 — 0: запись не зеркалируется |

Ошибок нет. v2 получает полную боевую нагрузку на чтение: по её логам, ошибкам и латентности видно, готова ли она, а пользователи об этом не знают.

## Наблюдение в Grafana

Дашборд «Стратегии деплоя core-api» (`k8s/grafana/dashboards/deploy-strategies.json`, подключается `k8s/grafana/install.sh`):

| Панель | Запрос |
|---|---|
| Запросов в секунду по версиям | `sum by (version) (rate(http_requests_total{app=~"core-api.*"}) * on (pod) group_left (version) taskscheduler_build_info)` |
| Доля трафика по версиям | тот же запрос, стопка в процентах: rolling — плавный переход, blue/green — ступенька, canary — лесенка |
| Реплики по версиям | `count by (version) (taskscheduler_build_info)` |
| Ответы 5xx по версиям | доля ошибок по версии, при выкатке без простоя — ноль |

`http_requests_total` от инструментатора FastAPI не знает версию, а `taskscheduler_build_info{version}` есть у каждого пода. Соединение по метке `pod` раскладывает запросы по версиям без изменений в vmagent.
