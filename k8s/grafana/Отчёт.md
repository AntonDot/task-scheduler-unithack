# Дашборды Grafana для Victory Group Task Scheduler

Приложение из ДЗ №1 работает в minikube (namespace `task-scheduler`). Метрики из ДЗ №4 собирает VictoriaMetrics, recording rules SLI/SLO/SLA из ДЗ №5 считает vmalert (namespace `monitoring`). В этом ДЗ рядом поставлена Grafana с двумя дашбордами:
- **«Task Scheduler — состояние приложения»** — своя сборка: статусы, RPS, ошибки, латентность, насыщение, SLA пробера, рантайм Python, бизнес-метрики;
- **«PostgreSQL Database»** — импорт дашборда 9628 с grafana.com для postgres-exporter.

## Состав и запуск

| Файл | Что внутри |
|---|---|
| `k8s/grafana/grafana-values.yaml` | values чарта `grafana-community/grafana` 14.6.0 (Grafana 13.3.2): источник данных, провайдер дашбордов, ресурсы, аннотации для vmagent |
| `k8s/grafana/dashboards/task-scheduler.json` | экспортированный JSON дашборда приложения |
| `k8s/grafana/install.sh` | импорт дашборда 9628, ConfigMap `grafana-dashboards`, `helm upgrade --install grafana` |

```bash
./k8s/grafana/install.sh
kubectl -n monitoring port-forward svc/grafana 3000:80          # http://localhost:3000
kubectl -n monitoring get secret grafana -o jsonpath='{.data.admin-password}' | base64 -d   # пароль admin
```

```
vmagent ──► VictoriaMetrics ◄── vmalert: recording rules SLI/SLO/SLA (ДЗ5)
                  ▲
                  │ PromQL (источник данных типа Prometheus, uid victoriametrics)
               Grafana ── ConfigMap grafana-dashboards: task-scheduler.json + postgresql.json (9628)
```

Grafana не хранит ничего, что настраивали руками. Источник данных и дашборды подключаются через provisioning из values и ConfigMap. Поэтому постоянный том не нужен: пересозданный под поднимается таким же. Провайдер перечитывает папку каждые 30 с, обновлённый ConfigMap подхватывается без рестарта. Grafana отдаёт свои метрики на `:3000/metrics`, аннотации `prometheus.io/*` подключают её к vmagent наравне с остальными подами.

## Источник данных

Используется один источник — **VictoriaMetrics** (`vm-single`, `http://vm-single-victoria-metrics-single-server.monitoring.svc.cluster.local:8428`):
- VictoriaMetrics отвечает по Prometheus HTTP API и понимает PromQL, поэтому подходит встроенный тип `prometheus`, отдельный плагин не нужен;
- `uid: victoriametrics` фиксирован: на него ссылаются панели дашборда;
- `timeInterval: 15s` равен интервалу опроса vmagent. От него Grafana считает `$__rate_interval`, так что `rate()` всегда покрывает несколько точек.

В VictoriaMetrics лежат все нужные ряды:
- метрики приложения из ДЗ №4: `http_*` от `prometheus-fastapi-instrumentator`, `process_*` и `python_*` от `prometheus-client`, бизнес-метрики `taskscheduler_*`;
- метрики postgres-exporter и RabbitMQ;
- push-метрики CronJob review-scraper;
- результаты recording rules ДЗ №5: `sli:*`, `slo:*`, `sla:*`.

## Дашборд приложения

Дашборд читается сверху вниз: от «всё ли в порядке» к «где именно и почему». Для детализации рантайма есть переменная **Сервис** (`$app`). Ссылка в шапке ведёт на дашборд PostgreSQL.

### 1. Обзор: четыре золотых сигнала

Верхний ряд отвечает на вопрос «работает ли приложение» за несколько секунд.

| Панель | Метрика | Почему |
|---|---|---|
| Сервисы | `min by (app) (up)` | статус каждого сервиса: отвечает ли его `/metrics`. Минимум по репликам, чтобы зависшая реплика не пряталась за здоровой |
| Трафик (Traffic) | `sum(rate(http_requests_total[$__rate_interval]))` | запросов в секунду ко всем FastAPI-сервисам |
| Ошибки (Errors) | доля `status="5xx"` | ошибки сервера, 4xx — ошибки клиента. Пороги 1 % и 5 % (алерт `ApiHighErrorRate`) |
| p95 API (Latency) | `histogram_quantile(0.95, …http_request_duration_seconds_bucket{app="core-api"})` | хвост времени ответа. Порог 0,5 с — граница SLO латентности |
| Память, Очередь (Saturation) | RSS / limits.memory, `rabbitmq_queue_messages_ready` | насколько процесс близок к OOMKilled и успевает ли automation-worker. Пороги — как у алертов ДЗ6 (75 % и 50 сообщений) |
| SLA за 1 ч | `sla:service:ratio_1h` | итог для клиента. Подробности в отдельной строке ниже |

### 2. RED: запросы, ошибки, длительность

RED (Rate, Errors, Duration) подходит для сервисов, обрабатывающих запросы: здесь это core-api и ml-worker.

| Панель | Метрика | Почему |
|---|---|---|
| Rate: запросов в секунду по сервисам | `sum by (app) (rate(http_requests_total))` | видно, на какой сервис пришла нагрузка |
| Errors: доля 5xx по сервисам | 5xx / все по `app` | в отличие от burn rate ДЗ5, который есть только у core-api, охватывает каждый FastAPI-сервис |
| Duration: латентность core-api | p50, p95, p99 и среднее (`sum / count`) | среднее скрывает хвост, перцентили показывают, что видит самый медленный пользователь. Линия — граница SLO 0,5 с |
| Ответы по классам кодов | `sum by (app, status) (rate(...))` | соотношение 2xx / 4xx / 5xx: рост 4xx — проблема клиентов или авторизации, 5xx — сервера |
| Самые частые маршруты core-api | `topk(10, sum by (method, handler) (...))` | метка `handler` — шаблон маршрута (`/api/v1/projects/{project_id}`), а не URL, поэтому кардинальность ограничена |

Перцентили считаются по корзинам гистограммы (0,1 / 0,5 / 1 с), поэтому это оценка с линейной интерполяцией внутри корзины. Например, p95 = 95 мс означает «внутри первой корзины».

### 3. SLA по пробёру

Отдельная строка с подсчётом SLA. Используются recording rules ДЗ №5:
- `sli:probe:good_minute` — минута хорошая, если синтетический пользователь прошёл сценарий «страница → вход → проекты → колонки → задачи» без ошибок быстрее 1 с;
- `sla:service:good_minute` — минута хорошая и по пробёру, и по реальному трафику (≥ 99 % без 5xx и ≥ 95 % быстрее 0,5 с);
- цель SLA — 99 % хороших минут.

| Панель | Метрика | Почему |
|---|---|---|
| **SLA за период** | `avg_over_time(sla:service:good_minute[$__range])` | главный показатель: доля хороших минут за интервал, выбранный в Grafana (час, сутки, месяц) |
| Простой | `(1 − SLA) × $__range_s` | то же в единицах, понятных клиенту: сколько времени сервис был недоступен |
| Пробер | `avg_over_time(sli:probe:good_minute[$__range])` | только синтетический пользователь (SLO 99,5 %): отличает «пробер не может войти» от «реальные запросы с ошибками» |
| Бюджет | `sla:service:error_budget_remaining_1h` | остаток бюджета ошибок SLA за час: 100 % — не тронут, 0 — исчерпан, меньше 0 — SLA нарушен |
| Проверка | `taskscheduler_probe_success`, `time() − taskscheduler_probe_last_timestamp_seconds` | результат последней проверки и её свежесть: если пробер завис, «OK» устаревает |
| SLA и SLO пробера за скользящий час | `sla:service:ratio_1h`, `slo:probe:ratio_1h` с линиями целей | динамика соответствия и запас до цели |
| Хорошие и плохие минуты | state timeline `sli:probe:good_minute`, `sla:service:good_minute` | когда именно были плохие минуты |
| Проверки пробера, На каком шаге падает, Длительность сценария | `taskscheduler_probes_total{result}`, `…_step_failures_total{step}`, гистограмма длительности | почему минута плохая: ошибка, конкретный шаг или медленный ответ |

Линии на дашборде не складываются стопкой. При стопке верхняя серия рисуется на уровне суммы всех, и, например, ошибки инцидентов выглядели бы равными числу дубликатов.

SLA за период и SLA за скользящий час — разные окна. Первый отвечает на вопрос клиента «сколько было за месяц», второй показывает, что происходит сейчас (по нему же срабатывает алерт `SLAAtRisk`).

### 4. Насыщение (USE)

USE (Utilization, Saturation, Errors) применяется к ресурсам, а не к запросам.

| Панель | Метрика | Почему |
|---|---|---|
| Память, % от лимита контейнера | `process_resident_memory_bytes` / limits.memory (512 / 384 / 256 МиБ) | лимит у каждого сервиса свой, абсолютные мегабайты не говорят, насколько близко OOMKilled. Линия 75 % — порог алерта |
| CPU, ядер | `rate(process_cpu_seconds_total)` | у контейнеров нет CPU-лимита, поэтому в ядрах, а не в процентах |
| Очередь RabbitMQ | `rabbitmq_queue_messages_ready`, `…_unacked`, `rabbitmq_consumers` | насыщение асинхронного контура. Рост ready при нуле консьюмеров — automation-worker упал |
| Соединения PostgreSQL | `pg_stat_activity_count` по состоянию, `pg_settings_max_connections` | пул соединений к базе — общий ресурс всех сервисов |
| PostgreSQL: транзакции и попадание в кэш | `pg_stat_database_xact_commit/rollback`, доля `blks_hit` | нагрузка на базу и хватает ли shared buffers |
| WebSocket-соединения | `taskscheduler_websocket_connections` | долгоживущие соединения держат память и дескрипторы core-api |

### 5. Рантайм Python: детализация

Метрики процесса от `prometheus-client`, фильтр по переменной **Сервис**. Нужны, когда верхние панели показали проблему и надо понять её природу.

| Панель | Метрика | Почему |
|---|---|---|
| Резидентная память (RSS) | `process_resident_memory_bytes` | рост без спада — утечка |
| CPU процесса | `rate(process_cpu_seconds_total)` | у какого пода нагрузка |
| Открытые файловые дескрипторы | `process_open_fds` | постоянный рост — утечка соединений |
| Сборки мусора в минуту | `python_gc_collections_total` по поколениям | частые сборки поколения 2 — много долгоживущих объектов, паузы |
| Аптайм процессов, Рестарты за период | `time() − process_start_time_seconds`, `changes(process_start_time_seconds[$__range])` | рестарт контейнера виден, даже если имя пода не изменилось |
| Версия Python | `python_info` | какая версия интерпретатора в каждом образе |

### 6. Бизнес-метрики

Метрики `taskscheduler_*` из ДЗ №4. Технически всё может быть зелёным, но пользователи не получают результат.

| Панель | Метрика |
|---|---|
| Входы в систему | `taskscheduler_logins_total{result}`: success, unknown_user, bad_password |
| Созданные задачи | `taskscheduler_tasks_created_total{source}`: пользователь, автоматизация, вебхук |
| Инциденты из отзывов | `taskscheduler_incidents_total{result}`: created, duplicate, error |
| События автоматизаций | `taskscheduler_automation_events_total{result}` |
| Пайплайн отзывов | push-метрики последнего прогона review-scraper |
| Время ответа LLM | p95 `taskscheduler_llm_request_duration_seconds` и обработки события автоматизации |

## Дашборд PostgreSQL Exporter

Импортирован дашборд [PostgreSQL Database](https://grafana.com/grafana/dashboards/9628) (ID 9628, ревизия 8) — стандартный дашборд для postgres_exporter. postgres-exporter v0.20.1 работает сайдкаром в поде `postgres-0` с ДЗ №4.

`install.sh` скачивает JSON с grafana.com и кладёт в тот же ConfigMap, что и дашборд приложения. Без доработки дашборд пустой: он писался под старый Helm-чарт Prometheus и ищет экспортер по меткам `kubernetes_namespace` и `release`. vmagent ставит нашим рядам метки `namespace` и `app`. Поэтому при импорте `jq` меняет:
- переменные: `namespace` = `label_values(pg_up, namespace)`, `release` (подпись app) = `app` пода экспортера, `instance` = его адрес;
- фильтр `release="$release"` в запросах панелей на `app="$release"`.

Сами панели не менялись. Дашборд показывает:
- версию и настройки PostgreSQL;
- QPS, коммиты и откаты;
- SELECT/INSERT/UPDATE/DELETE по базам;
- блокировки, активные и idle-сессии;
- попадание в кэш, buffers, конфликты и deadlocks.

Пустой остаётся только панель Start Time: метрика `pg_postmaster_start_time_seconds` в postgres-exporter v0.20 вынесена в коллектор `postmaster`, а он по умолчанию выключен.
