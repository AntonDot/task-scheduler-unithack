# SLI, SLO и SLA Victory Group Task Scheduler

Приложение из ДЗ №1 работает в minikube (namespace `task-scheduler`). Метрики из ДЗ №4 собирает VictoriaMetrics (namespace `monitoring`). Поверх них добавлены:
- пробер — синтетический пользователь;
- recording rules в vmalert: SLI, соответствие SLO, бюджет ошибок, burn rate;
- дашборд в vmui;
- управляемая инъекция сбоев в core-api для демонстрации.

## Состав и запуск

| Файл | Что внутри |
|---|---|
| `services/prober/` | пробер: сценарий пользователя через web, метрики `taskscheduler_probe*` |

| `k8s/slo/dashboards/slo.json` | дашборд vmui «Task Scheduler — SLI / SLO / SLA» |

## Выбранные метрики

| Метрика | Откуда | Что значит |
|---|---|---|
| `http_requests_total{app="core-api", status}` | ДЗ №4, `prometheus-fastapi-instrumentator` | запросы к API по шаблону маршрута и классу ответа (`2xx`, `4xx`, `5xx`) |
| `http_request_duration_seconds_bucket{app="core-api", le}` | ДЗ №4, тот же инструментатор | гистограмма времени ответа, границы 0,1 / 0,5 / 1 с |
| `taskscheduler_review_scraper_last_run_success`, `…_last_run_timestamp_seconds` | ДЗ №4, push из CronJob review-scraper | успех последнего прогона «отзывы → ml-worker → задача-инцидент» и время его окончания |
| `taskscheduler_probes_total{result}`, `taskscheduler_probe_duration_seconds`, `taskscheduler_probe_step_failures_total{step}` | новый пробер | результат и длительность сценария пользователя, шаг первой ошибки |

**Пробер** раз в 10 секунд проходит путь человека, открывающего доску. Он идёт через Service `web`, то есть через nginx, как браузер:

```
открыть страницу (/, в ответе есть <div id="root">) → войти (POST /auth/token, email + пароль)
  → список проектов (есть onegin-park) → колонки доски (не пусто) → задачи доски
```

Проверка успешна, если каждый шаг ответил 2xx с ожидаемым содержимым за 5 секунд. Пробер только читает, поэтому не создаёт задач и не искажает бизнес-метрики. Он ловит то, чего не видит core-api: упавший nginx, неготовые поды, сломанную сборку фронта.

Нагрузку на core-api для request-based SLI даёт сам пробер (около 0,5 запроса в секунду) и обычные пользователи. Пробы kubelet `/health` и `/ready` в метрики не попадают.

## SLI, SLO и SLA

Используются оба подхода:
- **RBSLO (request based):** доля хороших запросов среди всех.
- **TBSLO (time based):** доля хороших минут. Хорошесть минуты определяется по совокупности сигналов.

### SLI 1. Доступность API (RBSLO)

**SLI:** доля запросов к core-api, на которые не ответили 5xx. Ответы 4xx — это ошибки клиента (неверный токен, нет задачи), а не недоступность сервиса.

```
SLI_avail = Σ rate(http_requests_total{app="core-api", status!="5xx"}) / Σ rate(http_requests_total{app="core-api"})
```

**SLO:** 99,5 % запросов без 5xx за 28 дней. Бюджет ошибок — 0,5 % запросов.

### SLI 2. Латентность API (RBSLO)

**SLI:** доля успешных запросов к core-api, обслуженных быстрее 0,5 с (0,5 — граница корзины гистограммы).

```
SLI_lat = Σ rate(http_request_duration_seconds_bucket{app="core-api", status!="5xx", le="0.5"})
        / Σ rate(http_request_duration_seconds_count{app="core-api", status!="5xx"})
```

**SLO:** 99 % успешных запросов быстрее 0,5 с за 28 дней.

### SLI 3. Пробер: пользователь может работать с доской (TBSLO)

**SLI:** доля хороших минут. Минута хорошая, если за неё:
- пробер хотя бы раз прошёл сценарий;
- ни разу не упал;
- ни одна проверка не длилась дольше 1 с.

Минута без проверок, например когда пробер лежит, считается плохой, а не пропуском.

```
good_probe(t) = [Σ increase(probes{result="success"}[1m]) > 0]
              · [Σ increase(probes{result="failure"}[1m]) = 0]
              · [Σ increase(probe_duration_count[1m]) − Σ increase(probe_duration_bucket{le="1.0"}[1m]) = 0]
SLI_probe = avg_over_time(good_probe[окно])
```

**SLO:** 99,5 % хороших минут за 28 дней, бюджет около 3 ч 20 мин.

### SLI 4. Пайплайн отзывов → инциденты (TBSLO)

**SLI:** доля минут, когда последний прогон CronJob review-scraper успешен (все негативные отзывы дошли до ml-worker) и закончился меньше 150 с назад. CronJob запускается раз в минуту, так что отсутствие свежего прогона тоже считается плохой минутой.

```
good_pipeline(t) = [last_run_success = 1] · [time() − last_run_timestamp < 150 с]
```

**SLO:** 95 % хороших минут за 28 дней. Это внутренний асинхронный процесс: задержка инцидента на несколько минут допустима, поэтому цель ниже.

### SLA

**SLA для клиентов** (общий для набора SLO): сервис доступен не менее 99 % минут календарного месяца. Минута доступна, если одновременно:
- пробер прошёл без ошибок быстрее 1 с (SLI 3);
- за минуту не менее 99 % запросов core-api без 5xx (SLI 1);
- за минуту не менее 95 % успешных запросов быстрее 0,5 с (SLI 2).

```
good_sla(t) = good_probe(t) · [SLI_avail_1m ≥ 0,99] · [SLI_lat_1m ≥ 0,95]
SLA = avg_over_time(good_sla[месяц]) ≥ 99 %   (недоступно до 7 ч 18 мин в месяц)
```

Компенсация при нарушении: от 95 до 99 % — скидка 10 % месячной оплаты, ниже 95 % — 25 %. Пайплайн отзывов в SLA не входит: это внутренний процесс, клиенту обещана работа с доской, а не скорость появления инцидентов.

SLA мягче внутренних SLO (99 % против 99,5 %). Запас нужен, чтобы команда узнала о проблеме по SLO и бюджету ошибок раньше, чем будет нарушено обещание клиенту.

### Бюджет ошибок и burn rate

```
соответствие SLO         = хорошие / все за окно (RBSLO) или avg_over_time(good_minute[окно]) (TBSLO)
остаток бюджета ошибок   = 1 − (1 − соответствие) / (1 − цель)     1 — не тронут, 0 — исчерпан, < 0 — перерасход
burn rate                = (1 − SLI за 5 мин) / (1 − цель)          1 — тратим ровно по бюджету
```

**Окно в демонстрации — 1 час, а не 28 дней.** Так учения сдвигают соответствие SLO и бюджет за минуты. Выражения те же, в продакшене окно меняется на 28 дней (или календарный месяц для SLA).

## Реализация

**Recording rules** (`vmalert-values.yaml`) считаются каждые 30 с и пишутся обратно в VictoriaMetrics:

| Группа | Серии |
|---|---|
| `sli` | `sli:availability:ratio_rate1m/5m`, `sli:latency:ratio_rate1m/5m`, `sli:probe:good_minute`, `sli:review_pipeline:good_minute`, `sla:service:good_minute` |
| `slo` | `slo:<sli>:ratio_1h`, `slo:<sli>:error_budget_remaining_1h`, `slo:availability:burn_rate_5m`, `slo:latency:burn_rate_5m`, `sla:service:ratio_1h` |
| `slo-alerts` | `AvailabilityBudgetFastBurn`, `LatencyBudgetFastBurn` (burn rate > 14,4 в окнах 5 мин и 1 мин), `ProberFailing`, `ReviewPipelineStalled`, `SLAAtRisk` |

Порог 14,4 взят из SRE Workbook: с такой скоростью за час уходит 2 % месячного бюджета. Alertmanager не подключён (`-notifier.blackhole`), алерты видны в UI vmalert.

**Дашборд vmui** (`dashboards/slo.json`): по строке на SLA и на каждый SLI. В каждой строке:
- SLI за 1 и 5 минут;
- соответствие SLO за час с линией цели;
- остаток бюджета ошибок;
- burn rate (для RBSLO) или p50/p95 длительности сценария (для пробера).

Внизу — исходные метрики: запросы по коду ответа, результаты и шаги падений пробера. vm-single запущен с `-vmui.customDashboardsPath=/dashboards`, файл подключён из ConfigMap.

## Изменения поведения приложения для скринкаста

В core-api добавлен middleware `FaultInjectionMiddleware`. Он управляется переменными окружения и по умолчанию выключен:

| Переменная | Эффект |
|---|---|
| `CORE_FAULT_ERROR_RATE=0.3` | 30 % запросов `/api/` получают 503 |
| `CORE_FAULT_LATENCY_MS=800` | к каждому запросу `/api/` добавляется 800 мс |

Middleware стоит внутри метрик, поэтому внедрённые ошибки и задержки учитываются в `http_requests_total` и `http_request_duration_seconds` наравне с настоящими. `/health` и `/ready` не затрагиваются: Kubernetes не выводит поды из ротации, и деградация остаётся видна в SLI, а не превращается в рестарт. Переключение — скрипт `k8s/slo/fault.sh`: `kubectl set env` на Deployment, rolling update около 20 с.

Сценарии и ожидаемая реакция (проверено перед записью):

| Команда | Что меняется | SLI 1 доступность | SLI 2 латентность | SLI 3 пробер | SLI 4 отзывы | SLA |
|---|---|---|---|---|---|---|
| `fault.sh errors 0.3` | 30 % запросов API → 503 | падает до ~0,5–0,7 | без изменений | плохие минуты | — | плохие минуты |
| `fault.sh latency 800` | +800 мс к запросам API | без изменений | падает до 0 | плохие минуты (p95 ≈ 4,9 с) | — | плохие минуты |
| `fault.sh ml-down` | ml-worker → 0 реплик | без изменений | без изменений | без изменений | плохие минуты | без изменений |
| `fault.sh off` | всё возвращается | 1 | 1 | хорошие минуты | хорошие минуты | хорошие минуты |

Замеры через 2,5 минуты учений:
- **ошибки 30 %:** `sli:availability:ratio_rate1m` = 0,5, `slo:availability:burn_rate_5m` = 24,5, остаток бюджета за час −7,5. Алерт `SLAAtRisk` перешёл в firing, `AvailabilityBudgetFastBurn` — в pending;
- **задержка 800 мс:** `sli:latency:ratio_rate1m` = 0, p95 сценария пробера 4,9 с;
- **ml-worker выключен:** `sli:review_pipeline:good_minute` = 0, остальные SLI не изменились.

Последний сценарий показывает, зачем SLI разделены: падение асинхронного пайплайна не задевает пользователя у доски и не нарушает SLA, но тратит собственный бюджет.
