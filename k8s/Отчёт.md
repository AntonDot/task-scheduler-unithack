# Victory Group Task Scheduler в Kubernetes (minikube)

Приложение — таск-менеджер для digital-агентства: Kanban-доска, AI-черновики задач, автоматизации и уведомления. Здесь описано, как оно разворачивается в однонодовом кластере minikube.

## Состав архива

| Файл | Что внутри |
|---|---|
| `k8s/00-namespace.yaml` | Namespace `task-scheduler` |
| `k8s/01-config.yaml` | ConfigMap `app-config` и Secret `app-secrets` — конфигурация всех сервисов |
| `k8s/10-postgres.yaml` | PostgreSQL 16: StatefulSet + headless Service + PVC |
| `k8s/11-s3.yaml` | S3-хранилище вложений (RustFS): StatefulSet + headless Service + PVC |
| `k8s/12-rabbitmq.yaml` | RabbitMQ: StatefulSet + headless Service + PVC |
| `k8s/20-migrate-job.yaml` | Job `migrate`: миграции БД, создание бакета, демо-данные |
| `k8s/30-core-api.yaml` | core-api: Deployment (2 реплики) + Service |
| `k8s/31-web.yaml` | web (nginx + React SPA): Deployment (2 реплики) + Service NodePort |
| `k8s/40-ml-worker.yaml` | ml-worker: Deployment + Service |
| `k8s/41-mock-review-board.yaml` | mock-review-board: Deployment + Service |
| `k8s/42-automation-worker.yaml` | automation-worker: Deployment без Service |
| `k8s/43-review-scraper-cronjob.yaml` | review-scraper: CronJob раз в минуту |
| `k8s/build-images.sh` | Сборка образов в Docker-демоне minikube |
| `k8s/pack.sh` | Сборка этого архива (в репозитории) |
| скринкаст | Запуск, `kubectl get pods`, масштабирование, работа в UI |
| `services/*/Dockerfile`, `jobs/review-scraper/Dockerfile`, `apps/web/Dockerfile`, `apps/web/nginx/default.conf.template` | Dockerfile сервисов и шаблон конфига nginx |

## Запуск

```bash
minikube start --driver=docker --container-runtime=docker --cpus=4 --memory=6144

# Сборка в Docker-демоне minikube: образы сразу видны кластеру
eval $(minikube docker-env)
./k8s/build-images.sh
# или собрать локально и загрузить в minikube: ./k8s/build-images.sh --load
#   (внутри — docker build + minikube image load task-scheduler/<сервис>:dev)

kubectl apply -f k8s/
kubectl get pods -n task-scheduler -w

minikube service web -n task-scheduler   # откроет UI в браузере
```

Образы помечены тегом `dev`, в манифестах указан `imagePullPolicy: IfNotPresent`. Поэтому kubelet берёт локальный образ и не ходит за ним в Docker Hub. С тегом `latest` Kubernetes по умолчанию пытался бы скачать образ и падал бы с `ErrImagePull`.

Порядок запуска не нужно соблюдать вручную. Достаточно одного `kubectl apply -f k8s/`, а дальше компоненты ждут друг друга сами (см. ниже).

Логин без пароля: на странице входа указать `d.morozov@victorygroup.ru` (OWNER) или `a.kozlova@victorygroup.ru` (ASSIGNEE).

## Какие абстракции Kubernetes использованы

| Абстракция | Где | Зачем |
|---|---|---|
| **Namespace** | `task-scheduler` | Всё приложение изолировано в одном пространстве имён. `kubectl delete ns task-scheduler` удаляет установку целиком. |
| **ConfigMap** | `app-config` | Обычные настройки: адреса сервисов, флаги, имя бакета. Аналог `.env` из docker-compose (12-factor III). |
| **Secret** | `app-secrets` | Пароли БД, S3 и RabbitMQ, JWT-секрет, service-token. В поды попадают через `envFrom` и `secretKeyRef`. |
| **StatefulSet** + **PersistentVolumeClaim** | postgres, s3, rabbitmq | Сервисы с состоянием. StatefulSet даёт поду стабильное имя (`postgres-0`) и собственный том через `volumeClaimTemplates`. Данные переживают пересоздание пода. В minikube тома выдаёт встроенный provisioner `standard` (hostPath). |
| **Headless Service** (`clusterIP: None`) | postgres, s3, rabbitmq | DNS-имя указывает прямо на под StatefulSet, без балансировки: у каждого из этих сервисов один экземпляр. |
| **Deployment** | core-api, web, ml-worker, mock-review-board, automation-worker | Процессы без состояния. Deployment держит нужное число реплик, перезапускает упавшие и обновляет их через rolling update. Масштабирование — `kubectl scale`. |
| **Service ClusterIP** | core-api, ml-worker, mock-review-board | Стабильный адрес и балансировка между репликами внутри кластера. |
| **Service NodePort** | web (порт 30080) | Точка входа снаружи кластера: браузер → nginx. |
| **Job** | migrate | Разовый административный процесс (12-factor XII): `alembic upgrade head`, создание S3-бакета, демо-данные. Выполняется до успеха (`backoffLimit: 6`) и завершается. Остаётся в статусе `Completed`. |
| **CronJob** | review-scraper | В docker-compose скрейпер был вечным процессом с `sleep`. В Kubernetes расписанием управляет кластер: раз в минуту запускается под `scraper.py --once`, делает один проход и завершается. |
| **initContainers** | migrate, core-api, automation-worker | Замена `depends_on` из compose. Job ждёт, пока ответят postgres и s3, automation-worker — RabbitMQ. Поды core-api ждут, пока Job доведёт схему БД до Alembic head, и только после этого стартуют. |
| **readiness/liveness probes** | все долгоживущие поды | Readiness core-api (`/ready`) проверяет БД: реплика без БД выводится из Service и не получает трафик. Liveness (`/health`) перезапускает зависший процесс. У postgres — `pg_isready`, у RabbitMQ — `rabbitmq-diagnostics`. |
| **resources requests/limits** | все поды | Планировщик знает, сколько ресурсов нужно поду. Лимит памяти не даёт одному сервису съесть всю ноду. |
| **RollingUpdate** (`maxUnavailable: 0`) | core-api | При обновлении старая реплика гасится только после того, как новая прошла readiness — без простоя. |

## Как сервисы взаимодействуют

```
                         браузер
                            │  http://<minikube-ip>:30080
                            ▼
                   ┌──────────────────┐
                   │ web (nginx) ×2   │  Service web (NodePort)
                   │ SPA + прокси     │
                   └────────┬─────────┘
                 /api, /ws  │  core-api.task-scheduler.svc.cluster.local:8000
                            ▼
┌──────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ ml-worker    │◄──┤ core-api ×2      ├──►│ postgres-0       │  SQL + LISTEN/NOTIFY
│ (LLM, mock)  ├──►│ REST, WS, RBAC   │   └──────────────────┘
└──────▲───────┘   └──┬──────┬──▲─────┘   ┌──────────────────┐
       │              │      │  │      ──►│ s3-0 (RustFS)    │  вложения
       │              │      │  │         └──────────────────┘
       │              │ AMQP │  │ HTTP /internal (X-Service-Token)
       │              ▼      │  │
       │      ┌────────────┐ │  │
       │      │ rabbitmq-0 │ │  │
       │      └─────┬──────┘ │  │
       │            ▼        │  │
       │   ┌────────────────────┴┐
       └───┤ automation-worker   ├──► postgres-0
           └─────────────────────┘
┌─────────────────────────┐   HTTP    ┌───────────────────┐
│ review-scraper (CronJob)├──────────►│ mock-review-board │
│ раз в минуту            ├──┐        └───────────────────┘
└─────────────────────────┘  └──► ml-worker /webhook ──► core-api (создаёт задачу)
```

Сервисы находят друг друга по DNS-именам Service. Внутри namespace достаточно короткого имени (`postgres`, `core-api`), и эти имена совпадают с docker-compose. Поэтому значения переменных окружения в ConfigMap/Secret те же, что в `.env.example`.

Основные потоки:

1. **Браузер → web → core-api.** nginx отдаёт статику React-приложения и проксирует `/api/*` и WebSocket `/ws/*` в Service `core-api`. Браузер работает с одним origin, поэтому CORS не нужен. nginx резолвит имя бэкенда на каждый запрос через `kube-dns` (TTL 10 с). Поэтому при масштабировании или пересоздании подов core-api он сразу видит новые адреса. Имя указано полностью (`core-api.task-scheduler.svc.cluster.local`): собственный резолвер nginx не использует search-домены пода.
2. **core-api → PostgreSQL / S3.** Задачи, пользователи, роли и журнал хранятся в PostgreSQL. Вложения хранятся в S3 по ключу `tasks/{task_id}/{uuid}`. На диске пода нет ничего, поэтому реплики core-api взаимозаменяемы.
3. **WebSocket между репликами.** При двух и более репликах клиент может быть подключён к одной, а изменение прийти в другую. Реплика публикует событие через PostgreSQL `NOTIFY`, все реплики слушают канал (`LISTEN`) и рассылают событие своим WebSocket-клиентам. Поэтому `kubectl scale deployment/core-api --replicas=3` не ломает real-time обновления доски.
4. **Автоматизации.** core-api публикует событие задачи (`task_created`, `task_updated`, `column_changed`) в RabbitMQ (`automation.events`). automation-worker читает очередь, сверяет условия автоматизации по PostgreSQL и выполняет действия. Для этого он вызывает внутренние эндпоинты core-api (`/api/v1/tasks/internal/automation-event`, `/api/v1/push/internal/notify`) с заголовком `X-Service-Token`. Несколько реплик воркера — конкурирующие потребители одной очереди: каждое событие обрабатывает ровно один.
5. **AI-черновики.** core-api по HTTP вызывает ml-worker (`CORE_ML_WORKER_URL=http://ml-worker:8001`). В демо LLM замокан (`ML_USE_MOCK_LLM=true`).
6. **Отзывы → инциденты.** CronJob review-scraper раз в минуту забирает отзывы с mock-review-board и отправляет негативные в ml-worker. ml-worker разбирает их и создаёт задачу через core-api с `Idempotency-Key`. Повторно увиденный отзыв не создаёт дубль: дедупликация хранится в таблице `external_events`, а сам скрейпер состояния не хранит.

### Порядок старта

```
postgres-0, s3-0, rabbitmq-0      ── readiness: pg_isready, /health, rabbitmq-diagnostics
        │
        ▼
Job migrate  (init: ждёт postgres:5432 и s3/health)  → alembic upgrade head, бакет, seed
        │
        ▼
core-api ×2  (init: ждёт `alembic current` == head)  → readiness /ready
        │
        ▼
web ×2, ml-worker, CronJob review-scraper
automation-worker  (init: ждёт rabbitmq:5672)
```

Сервисы, у которых зависимость ещё не готова, не падают окончательно. core-api в фоне переподключается к RabbitMQ, а если зависимость пропадёт уже после старта, упавший под перезапустит Deployment. Кластер приходит к рабочему состоянию сам, без ручной последовательности команд.

## Масштабирование

```bash
kubectl scale deployment/core-api -n task-scheduler --replicas=4
kubectl scale deployment/web -n task-scheduler --replicas=3
kubectl scale deployment/automation-worker -n task-scheduler --replicas=3
kubectl get pods -n task-scheduler -o wide
```

Горизонтально масштабируются все Deployment: в процессах нет состояния (12-factor VI, VIII). Service сразу начинает балансировать запросы на новые поды, как только они проходят readiness. StatefulSet'ы (postgres, s3, rabbitmq) остаются в одном экземпляре: для учебной установки этого достаточно. В продакшене их заменяют управляемыми сервисами (Managed PostgreSQL, Object Storage, облачный брокер), а приложение переключают через переменные окружения без изменений кода.

## Сценарий демонстрации (скринкаст)

```bash
kubectl config use-context minikube
eval $(minikube docker-env) && ./k8s/build-images.sh   # заранее, до записи

kubectl apply -f k8s/                                   # 1. запуск
kubectl get pods -n task-scheduler -w                   # 2. поды до Running/Completed
kubectl get all,pvc,cm,secret,cronjob -n task-scheduler # 3. все объекты

kubectl scale deployment/core-api -n task-scheduler --replicas=4   # 4. масштабирование
kubectl scale deployment/web -n task-scheduler --replicas=3
kubectl get pods -n task-scheduler -l 'app in (core-api,web)'

minikube service web -n task-scheduler                  # 5. UI: логин, доска, перетаскивание задачи
```

Очистка: `kubectl delete ns task-scheduler`, `minikube stop`.
