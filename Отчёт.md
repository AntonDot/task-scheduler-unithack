# Отчёт: Victory Group Task Scheduler как приложение «12 факторов»

Репозиторий: <https://github.com/AntonDot/task-scheduler-unithack>

## 1. Доменная область

Таск-менеджер для digital-агентства (рекламные кампании, сайты, SMM для клиентов-застройщиков). Агентство ведёт несколько клиентских проектов. В каждом проекте есть своя Kanban-доска, участники с ролями и поток задач:

- менеджер (OWNER проекта) заводит задачи, назначает исполнителей, выставляет срочность и дедлайн, принимает работу в колонку «Готово»;
- специалисты (ASSIGNEE) двигают свои задачи по колонкам, комментируют, прикладывают файлы;
- все участники видят изменения доски в реальном времени, а уведомления о событиях по их задачам приходят в «колокольчик» и web-push.

Поверх ручной работы есть автоматизация:

- **конструктор правил** «триггер → условие → действие», например «задача попала в колонку Ревью → уведомить менеджера»;
- **входящие вебхуки** от внешних систем, например GitHub или CRM;
- **AI-черновики:** текст превращается в задачу с заголовком, описанием и срочностью;
- **мониторинг негативных отзывов** о клиенте: скрейпер забирает отзывы с площадки, а ML-воркер превращает каждый плохой отзыв в инцидент-задачу.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Frontend | React 18, TypeScript, Vite, TanStack Query, Zustand, dnd-kit; в образе раздаётся nginx |
| Backend | Python 3.12, FastAPI, uvicorn, SQLAlchemy 2.0 (async, asyncpg), Alembic, Pydantic v2 / pydantic-settings |
| СУБД | PostgreSQL 16 (данные, а через `LISTEN/NOTIFY` — шина событий WebSocket между репликами) |
| Объектное хранилище | S3 API (boto3); в compose — RustFS, S3-совместимая замена MinIO |
| Очередь | RabbitMQ 3 (aio-pika) — события для автоматизаций |
| AI | Anthropic Claude API или любой OpenAI-compatible API; по умолчанию mock (`ML_USE_MOCK_LLM=true`) |
| Зависимости | uv + `uv.lock` (Python), npm + `package-lock.json` (frontend) |
| Сборка и запуск | Docker, Docker Compose (профили), GitHub Actions (CI + сборка образов в GHCR) |

Фронт общается с бэкендом по HTTP/1.1 REST (`/api/v1/...`, Swagger на `/docs`) и WebSocket (`/ws/{project_id}`).

### Процессы

```
                    ┌──────────── web (nginx: SPA + прокси /api, /ws) ────────────┐
браузер ──HTTP/WS──▶│                                                             │
                    └──────────────▶ core-api ×N (FastAPI, REST + WebSocket) ─────┘
                                       │   │   │
                     PostgreSQL ◀──────┘   │   └──────▶ S3 (вложения)
                     (данные, NOTIFY)      ▼
                                       RabbitMQ ──▶ automation-worker ×N ──▶ core-api (internal API)
   mock-review-board ◀── review-scraper (clock) ──▶ ml-worker ──▶ core-api (idempotent create)
   migrate — разовый админ-процесс: миграции Alembic, бакет S3, демо-данные
```

| Процесс | Тип | Что делает |
|---|---|---|
| `core-api` | web | CRUD, RBAC, JWT-аутентификация, WebSocket, уведомления |
| `web` | web | SPA и обратный прокси на core-api |
| `ml-worker` | web | LLM-разбор текста в задачу, вебхук инцидентов |
| `automation-worker` | worker | Читает очередь RabbitMQ, выполняет правила автоматизаций |
| `review-scraper` | clock | Раз в `SCRAPER_INTERVAL_SECONDS` опрашивает площадку отзывов; умеет `--once` для cron |
| `mock-review-board` | web | Эмулятор внешней площадки отзывов для демо |
| `migrate` | admin, one-off | `alembic upgrade head`, создание бакета, seed; завершается |

По умолчанию `docker compose up` поднимает сам таск-менеджер: postgres, s3, migrate, core-api и web. Этого хватает для CRUD, и такой набор не нагружает машину. Профиль `--profile full` добавляет автоматизации и AI.

Полный CRUD для следующих ДЗ есть у задач, колонок, тегов, комментариев, вложений и автоматизаций.

## 4. Соответствие 12 факторам

Ниже по каждому фактору: что требует методология, как это сделано в приложении и где это видно в коде. Изменения, которые понадобились для соответствия, отмечены словом **«доработано»** (до доработки в проекте было так, как в описанном рядом антипаттерне).

### I. Кодовая база — одна кодовая база, много развёртываний

- Один git-репозиторий на всё приложение. Сервисы — это процессы одного приложения, у них общий релизный цикл и общий `docker-compose.yml`. Поэтому монорепозиторий не превращается в «несколько приложений».
- Из одного и того же коммита разворачиваются dev (`docker compose up` на ноутбуке), CI (`integration-smoke` в `.github/workflows/main.yml`) и сервер (`scripts/deploy.sh`). Окружения отличаются только `.env` и тегом образа.
- Общего кода с другими приложениями нет. Сервисы не импортируют модули друг друга и общаются только по HTTP и через очередь.

### II. Зависимости — явно объявлять и изолировать

- Манифесты: `pyproject.toml` у каждого Python-сервиса и `package.json` у фронта. Версии зафиксированы lock-файлами `uv.lock` и `package-lock.json`, они лежат в репозитории.
- **Доработано:** раньше Dockerfile делали `pip install .`. Lock-файл при этом игнорировался, а у трёх сервисов его не было вовсе. Теперь `uv.lock` есть у всех, а образ ставит зависимости строго по нему: `uv sync --frozen`. Если lock расходится с манифестом, сборка падает. Фронт собирается через `npm ci` вместо `npm install`. CI ставит зависимости так же: `uv sync --frozen --extra dev` — для всех пяти Python-сервисов (automation-worker добавлен в матрицу CI).
- Изоляция: каждый сервис ставится в свой venv (`/opt/venv` в образе, `.venv` локально) внутри своего контейнера. Системные пакеты не используются. `.dockerignore` не даёт локальному `.venv` попасть в образ.
- Как это проявилось на деле. Исходный `main` при `docker compose up` падает на старте automation-worker с `ImportError: ... requires that the Python 'greenlet' library is installed`: `pip install .` подтянул SQLAlchemy без транзитивной зависимости. С lock-файлом тот же сервис стартует.

### III. Конфигурация — хранить в окружении

- Весь конфиг читается из переменных окружения через `pydantic-settings`. У каждого сервиса свой префикс: `CORE_`, `ML_`, `AUTOMATION_`, `SCRAPER_`. В compose переменные попадают из `.env` (`env_file`). Файл `.env` в git не коммитится, `.env.example` описывает все переменные.
- **Доработано:** раньше в коде были дефолты `jwt_secret="dev-secret-key"`, `service_token="dev-service-token"`, webhook-ключа и `localhost`-адресов БД и очереди, а `dev_login` (вход без пароля) был включён по умолчанию. Теперь у секретов и адресов бэкинг-сервисов дефолтов нет: без переменной процесс не стартует. Проверка — `tests/test_twelve_factor.py::TestConfig`. `CORE_DEV_LOGIN` по умолчанию `false`.
- **Доработано:** раньше адреса соседних сервисов и порт бэкенда были зашиты в `docker-compose.yml`, `nginx.conf`, `vite.config.ts` и `smoke.sh`. Теперь nginx получает `PORT` и `CORE_API_URL` из окружения (шаблон `apps/web/nginx/default.conf.template`), Vite берёт `CORE_API_URL`, а smoke- и e2e-тесты — `E2E_*`.
- Тест на правильное разделение: репозиторий можно опубликовать хоть сейчас, в нём нет ни одного реального секрета. Публичный репозиторий именно так и выложен.

### IV. Сторонние службы — как подключаемые ресурсы

- PostgreSQL, S3, RabbitMQ и LLM API подключаются по URL и учётным данным из конфига: `CORE_DATABASE_URL`, `CORE_S3_ENDPOINT_URL` / `CORE_S3_ACCESS_KEY`, `CORE_RABBITMQ_URL`, `ML_LLM_BASE_URL` / `ML_LLM_API_KEY`. Замена локального ресурса на облачный — это смена переменной без правок кода.
- **Доработано:** раньше вложения писались в каталог `/app/uploads` контейнера core-api, то есть локальный диск сервера был частью приложения. Теперь файлы лежат в S3-совместимом хранилище (`services/core-api/app/storage.py`, boto3), а в БД хранится только `storage_key`.
- Пример взаимозаменяемости из этой же работы. Сначала хранилищем был выбран MinIO, но его образы перестали публиковаться на Docker Hub. MinIO заменён на RustFS одной правкой `image:` в compose, код и тесты не менялись. На сервере таким же образом подключаются AWS S3 или Yandex Object Storage.
- RabbitMQ и ML-воркер подключаются опционально. Без `CORE_RABBITMQ_URL` core-api работает, просто не публикует события автоматизаций. Если URL задан, но очередь ещё не поднята (например, профиль `full` запустили позже), core-api переподключается к ней в фоне каждые 10 с, без рестарта. Без `CORE_ML_WORKER_URL` AI-ручка отвечает 503 «не настроено», а при недоступном ml-worker — 502.
- Бакет создаётся в любом S3: на AWS вне `us-east-1` передаётся `LocationConstraint`, а ошибка доступа (403) не маскируется попыткой создать бакет.

### V. Сборка, релиз, выполнение — строго разделять стадии

- **Сборка (build):** код и lock-файлы превращаются в Docker-образ. Образ содержит код и зависимости, но не конфиг. В него зашивается идентификатор релиза `APP_VERSION` (аргумент сборки, равный короткому sha коммита). В CI это делает `.github/workflows/release.yml`: на push в `main` и теги `v*` он собирает 6 образов и пушит их в GHCR с тегом `<sha>` (и `<vX.Y.Z>` для тегов).
- **Релиз (release):** конкретный тег образов плюс `.env` окружения. Compose ссылается на образы по `${REGISTRY}/<сервис>:${APP_VERSION}`.
- **Выполнение (run):** `docker compose up -d --no-build` запускает готовый релиз.
- **Доработано:** раньше `scripts/deploy.sh` делал на сервере `git pull` и `docker compose build`, то есть собирал код прямо в продакшене. Версий у образов не было, откатиться было некуда. Миграции запускались вручную через `docker compose exec`. Теперь `deploy.sh` только копирует `docker-compose.yml`, делает `docker compose pull` нужного `APP_VERSION` и `up --no-build`. Откат — тот же вызов с предыдущим тегом, пока схема БД совместима с прошлой версией: миграции Alembic автоматически не откатываются (подробнее — в разделе 6). Перед запуском `deploy.sh` проверяет, что все образы релиза действительно скачаны (GHCR требует `docker login` на сервере). Изменить код на стадии запуска нельзя: образы неизменяемы, а Python-процессы работают не от root.
- Тег релиза — 7 символов sha коммита (`${GITHUB_SHA::7}` в CI, `git rev-parse --short=7 HEAD` локально), так что локальная сборка и образ из GHCR называются одинаково.

### VI. Процессы — без состояния

Все процессы приложения хранят состояние только во внешних службах, и любой из них можно перезапустить или запустить в нескольких экземплярах. **Доработано** четыре места:

| Было | Стало |
|---|---|
| Вложения на локальном диске контейнера core-api; при пересоздании контейнера терялись | S3; файл, загруженный через одну реплику, скачивается через другую |
| WebSocket-подписчики в памяти процесса: при двух репликах событие получали только клиенты той реплики, которая обработала запрос | События публикуются через PostgreSQL `NOTIFY`, каждая реплика делает `LISTEN` и рассылает своим сокетам (`app/websocket_manager.py`). Есть переподключение при обрыве, TCP keepalive и таймаут 2 с на `NOTIFY` (зависшее соединение рвётся и открывается заново, событие доставляется локально, запрос не блокируется); payload ужимается до лимита NOTIFY в 8000 байт |
| ml-worker помнил обработанные события в Python-множестве `_processed_events`: после рестарта задачи дублировались, при двух репликах дубли не ловились | Таблица `external_events` в PostgreSQL. ml-worker проверяет `GET /internal/external-events/{id}` до вызова LLM, а создание задачи идёт с заголовком `Idempotency-Key`. Ключ события занимается первым шагом транзакции, до создания задачи: при гонке двух реплик второй запрос ждёт на первичном ключе и получает 409, не породив ни задачи, ни уведомлений |
| review-scraper вёл файл `processed_ids.json` на volume | Скрейпер не хранит ничего; дедупликацию выполняет сервер (см. строку выше) |

Сессии тоже без состояния: аутентификация на JWT, и токен проверяется любой репликой. Аватары и настройки пользователей хранятся в БД.

Проверено на живом стеке: WebSocket подключён к реплике B, задача создаётся через реплику A, событие приходит в сокет B. Вложение загружено через A и скачано через B.

### VII. Привязка портов — экспортировать сервисы через порт

- Каждый HTTP-сервис самодостаточен: uvicorn встроен в приложение, и наружу оно отдаётся через порт. Внешний веб-сервер или контейнер приложений не нужен.
- **Доработано:** порт берётся из переменной `PORT` (`ENV PORT=...` в Dockerfile, `uvicorn --port "$PORT"`; у nginx — `listen ${PORT}`). На какой порт хоста его опубликовать, решает окружение (`CORE_API_PORT`, `WEB_PORT` и т. д. в compose).
- Сервисы обращаются друг к другу как к ресурсам по URL из конфига: `ML_CORE_API_URL=http://core-api:8000`.
- nginx в образе `web` — это собственный HTTP-сервер фронтенда (статика + прокси), а не общий сервер, в который «встроено» приложение. Каждый образ слушает свой порт. Имя бэкенда nginx резолвит на каждый запрос (`resolver`, TTL 10 с), а не один раз при старте, поэтому пересозданный или отмасштабированный core-api подхватывается без перезапуска web.

### VIII. Параллелизм — масштабирование через модель процессов

- Работа разделена на типы процессов: web (`core-api`, `ml-worker`, `web`), worker (`automation-worker`), clock (`review-scraper`), admin (`migrate`). Каждый тип масштабируется отдельно, количеством экземпляров.
- Горизонтальное масштабирование возможно благодаря фактору VI. Несколько реплик core-api корректно делят WebSocket-события, вложения и дедупликацию (проверено с двумя репликами). Несколько `automation-worker` (`docker compose --profile full up --scale automation-worker=3`) читают одну очередь, и RabbitMQ раздаёт сообщения между ними. Внутри одного воркера события обрабатываются последовательно, чтобы правила по одной задаче применялись в порядке очереди; пропускная способность растёт числом процессов, а не потоков. Портов у воркеров нет, поэтому масштабирование ничему не мешает.
- «Главного» процесса нет. Все экземпляры одного типа равноправны, координация — через PostgreSQL и RabbitMQ.
- Ограничение текущего compose: у `core-api` порт опубликован на хост (`8000`, для Swagger и e2e-тестов). Поэтому `--scale core-api=N` в compose требует убрать публикацию порта и ходить через `web`. Само приложение к этому готово, а балансировку на несколько реплик добавим в следующих ДЗ (Kubernetes / балансировщик).

### IX. Утилизируемость — быстрый старт и корректное завершение

- **Быстрый старт. Доработано:** раньше core-api на каждом старте прогонял миграции и seed в `entrypoint.sh`. Теперь это разовый процесс `migrate`, а старт core-api — это только открытие соединений. Приложение готово к запросам меньше чем через секунду (по логам между `Started server process` и `Application startup complete` — около 0,1 с). Весь стек по умолчанию поднимается за ~15 с, включая healthcheck.
- **Корректное завершение по SIGTERM. Доработано:**
  - core-api и ml-worker: uvicorn по SIGTERM перестаёт принимать запросы и дорабатывает текущие (`--timeout-graceful-shutdown 20`). В `lifespan` закрываются WebSocket-клиенты (код 1012) и соединения с PostgreSQL и RabbitMQ. Фронт (`useTasksRealtime`) переподключается с экспоненциальной задержкой и перезапрашивает доску: события, пропущенные за время переподключения, не теряются.
  - automation-worker: раньше SIGTERM не обрабатывался, и процесс убивался по таймауту. Теперь по сигналу он отменяет подписку на очередь, дожидается обработки сообщений в работе и закрывает соединения.
  - review-scraper: раньше бесконечный `while True` с `sleep`. Теперь сигнал прерывает ожидание между циклами.
  - Процессы стартуют через `exec` и получают сигнал как PID 1. Замер `docker compose stop`: automation-worker — 0,3 с, review-scraper — 0,3 с, core-api — 0,6 с, все с кодом 0.
- **Устойчивость к внезапной гибели.** Сообщение RabbitMQ подтверждается только после обработки, поэтому при `kill -9` воркера оно вернётся в очередь и достанется другому (семантика at-least-once: действия автоматизаций при такой повторной доставке могут выполниться дважды, идемпотентен только путь «внешнее событие → задача» через `Idempotency-Key`). Соединение `LISTEN` переподключается само.
- Readiness и liveness разделены: `/health` — процесс жив, `/ready` — БД отвечает (на него смотрит healthcheck compose, позже — пробы Kubernetes).

### X. Паритет разработки и продакшена — окружения максимально похожи

- Везде один и тот же `docker-compose.yml`, одни и те же образы и одни и те же бэкинг-сервисы: PostgreSQL 16, S3, RabbitMQ 3. В разработке нет SQLite или «локальной папки вместо S3». Разница только в `.env` и `APP_VERSION`.
- CI поднимает тот же compose (`--profile full`) и гоняет smoke- и e2e-тесты против него.
- Для локального запуска без Docker бэкинг-сервисы всё равно берутся из compose (`docker compose up -d postgres s3`), а конфиг — из того же `.env` (см. README).
- Исключение: юнит-тесты core-api используют SQLite in-memory для скорости. Миграции и работа приложения на настоящем PostgreSQL проверяются в интеграционном прогоне CI (compose со всеми сервисами). Доставка WebSocket-событий между двумя репликами через `NOTIFY` проверена вручную на живом стеке (см. фактор VI); в CI работает одна реплика.
- Разрыв по времени между кодом и продом сокращён: каждый коммит в `main` автоматически превращается в образы в GHCR, а деплой — одна команда.

### XI. Журналирование — логи как поток событий

- **Доработано:** все процессы пишут в stdout одну JSON-строку на событие (`ts`, `level`, `service`, `logger`, `message`, `exc_info`). Логи uvicorn, включая access-лог, идут через тот же форматтер. Уровень задаётся переменной `*_LOG_LEVEL`. Раньше формат был разный, а у core-api логирование не было настроено вовсе.
- Приложение не открывает и не ротирует файлы логов. Сбор, хранение и маршрутизация — задача окружения: сейчас `docker compose logs`, в следующих ДЗ — сборщик логов.
- Попутно из логов убран вывод URL RabbitMQ с паролем.

### XII. Административные процессы — разовые процессы

- **Доработано:** миграции Alembic, создание бакета S3 и загрузка демо-данных выполняются отдельным сервисом `migrate` (`services/core-api/scripts/migrate.sh`). Он запускается из того же образа и с тем же `.env`, что и core-api, отрабатывает и завершается. core-api ждёт `service_completed_successfully`, так что приложение не стартует на несмигрированной схеме.
- Раньше миграции и seed были зашиты в старт веб-процесса, а в `deploy.sh` дополнительно запускались вручную через `docker compose exec`.
- Разовые задачи запускаются так же: `docker compose run --rm migrate`, `docker compose run --rm review-scraper python scraper.py --once`, `docker compose run --rm core-api python -m scripts.seed`. Схема БД меняется только миграциями: seed больше не делает `create_all`.

## 6. Что сознательно не доведено до идеала

- **`mock-review-board`** хранит отзывы в памяти. Это эмулятор чужой внешней площадки для демо, а не часть нашего приложения, и после рестарта он восстанавливает исходный набор отзывов.
- **Вход без пароля** (`CORE_DEV_LOGIN=true`) включён в `.env.example` для демо. В коде он выключен по умолчанию, на сервере его не включают.
- **Перенос данных старых инсталляций.** Миграция 0022 не переносит в S3 файлы с дисков старых инсталляций (она только переименовывает колонку) и не заполняет `external_events` из старого `processed_ids.json` скрейпера. На уже работавшем сервере после обновления скрейпер один раз заново отправит старые негативные отзывы, и по ним создадутся задачи. Для учебного стенда данных нет. Для боевой инсталляции и то и другое делается разовым скриптом по фактору XII.
- **Откат через изменение схемы.** Миграция 0022 не обратно совместима: старый образ ждёт `stored_path`, а в схеме уже `storage_key`. Откатить образ «через» такую миграцию нельзя без `alembic downgrade`. Правильный путь для продакшена — expand/contract (сначала добавить новое, через релиз убрать старое). Аварийный fallback `alembic stamp head` теперь срабатывает только для баз без `alembic_version`, созданных до Alembic. На базе под управлением Alembic упавшая миграция останавливает релиз, а не маскируется.
- **nginx в образе `web`** запускается от root, как в официальном образе; Python-процессы работают от непривилегированного пользователя.
- **Публикация порта core-api** мешает `--scale core-api` именно в compose (см. фактор VIII). Балансировка и Kubernetes будут в следующих ДЗ.
